ROBUST RANDOMNESS TESTS -- SUITE EXPANSION (2026)
=================================================

This document supplements the original rtest suite. For the underlying theory
and the initial tests (0-21), see README.md and robust/doc/tests-description.tex.


1. OVERVIEW
-----------

The robust framework replaces the usual asymptotic p-values -- which often lack
proven error bounds -- with a two-sample Kolmogorov-Smirnov comparison. For a
test statistic t(B) we form two samples:

  U: t applied directly to blocks from the tested generator A;
  V: t applied to blocks XOR-ed with a fixed reference ("etalon") E (that is, A xor E).

If A is truly random, then A xor E is also random for any fixed E, whatever the
quality of E. Since the same code for t is applied to both samples, a rough
approximation or a coding error affects U and V the same way and cancels in the
comparison.

The scope of that argument matters, and an earlier version of this file
overstated it. It holds for a deterministic function applied identically to
both samples, and under those assumptions it is what keeps the null calibration
intact: an inaccurate statistic should not by itself make a good generator
fail. It is not a guarantee against arbitrary implementation errors. It does
not cover an error that makes the two paths consume different amounts of input,
or that leaves one path depending on buffer state carried over from the other.
An implementation error will generally cost sensitivity and change individual
p-values, so it is not correct to say it can never cause a good generator to be
rejected. The README states it in these same terms; that phrasing is the one to
quote.


2. THE EXPANSION
----------------

We added twenty tests (numbers 22-41), adapting statistics from the Diehard,
Dieharder, and NIST batteries. The suite now has 41 test families and covers the
Diehard battery and most of NIST STS. The one NIST test with no
counterpart here is Overlapping Template Matching (SP 800-22 section 2.8),
as noted in section 6 below. Each new test and its origin:

  23  Count-the-1s (stream)            Diehard + Dieharder    test_count1s_stream.c
  24  Count-the-1s (specific bytes)    Diehard + Dieharder    test_count1s_byte.c
  25  Parking Lot                      Diehard + Dieharder    test_parking.c
  26  Squeeze                          Diehard + Dieharder    test_squeeze.c
  27  OPERM5                           Diehard + Dieharder    test_operm5.c

  29  DAB DCT (adapted)                Dieharder              test_dab_dct.c
  30  DAB Filtering (adapted)          Dieharder              test_dab_filtering.c
  31  Linear Complexity                NIST + Dieharder       test_linear_complexity.c
  32  Random Excursions                NIST                   test_random_excursions.c
  33  Random Excursions Variant        NIST                   test_random_excursions_variant.c
  34  3D Spheres                       Diehard + Dieharder    test_3d_spheres.c
  35  Marsaglia-Tsang GCD              Dieharder              test_gcd.c

Tests 29 and 30 are adaptations, not ports. Dieharder's DAB DCT takes 256-point
DCTs of many blocks and reports the maximum coefficient; ours takes low-frequency
energy from a single large DCT. Dieharder's DAB filtering is a different
construction; ours applies a fixed 8-tap zero-sum filter to non-overlapping
blocks. This is acceptable here because the robust scheme compares a statistic
against itself: both samples are produced by the same code, so the statistic
need not reproduce a published one to give a valid p-value. It does mean results
from these two are not comparable to Dieharder's.

("Diehard" is Marsaglia's battery, "Dieharder" R. G. Brown's extension, "NIST"
the NIST Statistical Test Suite, SP 800-22.)


3. AI-ASSISTED IMPLEMENTATION
-----------------------------

The statistics for tests 22-41 were drafted with AI assistance, in a loop:

  1. an initial version written from the test's specification (Codex);
  2. independent review for logic and memory errors (Claude Code);
  3. a check against the original source papers (NotebookLM);
  4. a human audit, compilation under sanitizers, and the checks in section 6.

Model agreement reduces mistakes but does not prove correctness. It is only safe
because of section 1: any error left in a statistic can cost sensitivity, never
validity.


4. REPORTING: BEST OBJECTIVE IN SWEEP
-------------------------------------

The KS objective is not always monotone in the sample size. As the number of
blocks p grows toward the end of the file, failing and passing windows mix and
the detection signal can weaken ("wash out"). A sweep should therefore report
the best (smallest) objective observed during the adaptive doubling/bisection
search, not the value at the file ceiling. Using the ceiling value undercounts
real detections; it was also the source of an apparent "XOR amplification"
effect, which disappeared once the best-in-sweep value was used. XOR mode does
not add signal -- it only consumes data faster, so it reaches the ceiling sooner.


5. BUILDING AND RUNNING
-----------------------

Dependencies:
  GMP, GSL   -- statistics and the exact (multiprecision) KS backup
  OpenSSL    -- deterministic reference generators (bit-for-bit across platforms)

  Debian/Ubuntu:  apt-get install libgmp-dev libgsl-dev libssl-dev
  macOS:          brew install gmp gsl openssl

Run "make" in robust/ to build the rtest binary. A single test is invoked as

  ./rtest -x -f GENERATOR -e REFERENCE -p P -q Q -n N -t T -d D -o OUT

(-x XOR mode; -f file under test; -e reference, fixed in advance; -t test number;
-n values per call; -d dimension; -p, -q the two sample sizes).


6. VALIDATION
-------------

The authoritative account is docs/validation.md. It states what the campaign
does and does not establish, why its exact p-values cannot be reproduced, and
which rows are affected by the KS saturation. Read it rather than this summary
if the two ever disagree.

In brief: tests 22 to 31 -- not all of 22 to 41 -- were run against nine NIST
reference generators. The three intended controls (Blum-Blum-Shub, Linear
Congruential, Micali-Schnorr) crossed the 10^-10 threshold on no test, and the
other six crossed it on at least one.

Three qualifications, all of which earlier versions of this file left out:

  - Those are recorded exploratory outcomes, not an estimated false-positive
    rate. Nine generators over ten tests cannot establish one, and the minimum
    over a sweep is biased low by the search itself.
  - 36 of the 90 rows report a p-value of exactly 1.0, through the default KS
    backend which is known to underflow at those sample sizes. The campaign is
    not clean; see docs/validation.md and the measurements under
    reproducibility/campaign-2026-05-02/saturation-check/.
  - Tests 32/33 (Random Excursions) decline on streams that yield too few
    excursion cycles, which NIST specifies. A decline is the test reporting its
    own limit given the sample size and data available. It is NOT evidence
    against the generator: these two tests also decline at some sample sizes on
    this repository's own random-like SHAKE-256 fixture, which is the example
    of a stream that should look random.

There is no no-XOR comparison in this repository. The campaign metadata records
XOR mode as enabled throughout, so any claim that results agreed with and
without the XOR step is not supported by what is committed here. An earlier
version of this file asserted that agreement; it should not have.


7. LIMITATIONS
--------------

- Overlapping Template Matching (NIST) is not yet ported; it is the only
  remaining gap for full NIST STS coverage.
- The Diehard 31x31 binary-rank test is omitted as redundant with the
  implemented 32-bit rank tests.
- XOR mode consumes bits twice as fast as plain mode, so it reaches
  end-of-file earlier.
- The sweep harness caps p and q at 10,000.
